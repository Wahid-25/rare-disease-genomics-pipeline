20. Automatic Clinical-Report JSON Generation and Report Population
===================================================================

The pipeline includes an automated workflow that converts final case results into a structured clinical-report draft. This removes the need to copy every variant, annotation and patient field manually into the browser-based report builder.

The workflow creates a JSON file after candidate ranking is complete. The JSON contains selected findings, patient metadata, phenotype information, methodology, warnings, provenance and report-level information. The report builder can then load this file and automatically populate its editable fields.

The automatically generated report remains a **draft**. It must be reviewed by an analyst before it is saved as a reviewed JSON file or exported as a PDF.

20.1 Purpose of the Automated Workflow
--------------------------------------

The automatic clinical-report workflow was developed to:

#. Convert pipeline outputs into a consistent report structure.
#. Reduce manual transcription errors.
#. Preserve the relationship between a report and its source result files.
#. support multiple findings within one case.
#. include rare-disease, compound-heterozygous, structural, repeat and pharmacogenomic information when available;
#. add protected patient metadata without placing it in public code;
#. generate a checksum for file-integrity verification;
#. register the report JSON in the pipeline summary;
#. open the correct report automatically through a local browser;
#. maintain a clear distinction between automated drafting and analyst-approved interpretation.

The workflow improves consistency but does not replace interpretation. Candidate selection and automatically generated narrative text must still be checked against the underlying evidence.

20.3 Position Within the Pipeline
---------------------------------

The report JSON is generated after the main analysis tables and pipeline summary have been produced.

The simplified sequence is:

.. code-block:: text

   Input preparation
   ↓
   VCF preflight
   ↓
   Variant annotation
   ↓
   Disease and phenotype matching
   ↓
   Inheritance and ploidy assessment
   ↓
   Candidate scoring and ranking
   ↓
   Final master candidate table
   ↓
   Clinical-report draft JSON generation
   ↓
   Checksum generation
   ↓
   Pipeline-summary registration
   ↓
   Local report population
   ↓
   Analyst review and export

The report generator depends on earlier pipeline stages. It should therefore not be treated as a separate annotation tool. It organises evidence that has already been generated by the workflow.

20.4 Automatic Invocation by the Main Pipeline
----------------------------------------------

The report generator is registered as a required pipeline script in:

.. code-block:: text

   pipeline/run_case_pipeline.sh

Near the end of a successful case run, the pipeline executes:

.. code-block:: text

   python3 \
   pipeline/case_workflow/22_build_clinical_report_json.py \
   "$CASE_ID"

The pipeline displays a stage similar to:

.. code-block:: text

   [5] Building clinical-report draft JSON

A successful run produces a message similar to:

.. code-block:: text

   CLINICAL REPORT DRAFT JSON CREATED

The pipeline then records the JSON path and checksum in the final case summary.

This means that a user who runs the normal case workflow does not need to execute the report generator separately.

20.5 Manual JSON Generation
---------------------------

The generator may also be executed manually when a report needs to be rebuilt after metadata or report-generation logic has changed.

The command is:

.. code-block:: text

   cd ~/rare_disease_project

.. code-block:: text

   python3 \
   pipeline/case_workflow/22_build_clinical_report_json.py \
   <case_id>

For example:

.. code-block:: text

   python3 \
   pipeline/case_workflow/22_build_clinical_report_json.py \
   patient_06_pku

Manual regeneration does not repeat the complete annotation pipeline. It reads the existing final case outputs and rebuilds the report JSON.

Before manual regeneration, the required result files for that case must already exist.

20.6 Main Input Files
---------------------

The report generator reads several pipeline outputs. The exact availability depends on the case and the analysis route.

The primary candidate source is:

.. code-block:: text

   results/cases/<case_id>/final/<case_id>.master_candidate_ranking.tsv

This table contains ranked disease and pharmacogenomic candidates assembled by the workflow.

The generator may also read:

- results/cases/<case_id>/annotated/<case_id>.vep_best_transcripts.tsv
- results/cases/<case_id>/final/<case_id>.pipeline_summary.tsv
- results/cases/<case_id>/final/<case_id>.resource_mode.tsv
- input/cases/<case_id>/staged/<case_id>.pipeline_phenotypes.txt
- input/cases/<case_id>/metadata/report_metadata.json

Additional supporting inputs may include:

- local or official pharmacogenomic tables;
- repeat-expansion output;
- inheritance and ploidy results;
- compound-heterozygous aggregation results;
- pipeline provenance;
- resource-mode information;
- HPO phenotype terms.

The generator is designed to tolerate the absence of optional inputs by recording warnings or leaving unsupported fields empty rather than inventing values.

20.7 Candidate Selection
------------------------

The master candidate table may contain hundreds of rows. The generator therefore applies automatic selection rules to create a manageable report draft.

The automatic selection process may include:

- identifying the highest-priority disease group;
- selecting the strongest candidates associated with that disease;
- retaining multiple genes when they support the same disease group;
- including relevant compound-heterozygous partners;
- including supported repeat-expansion findings;
- including pharmacogenomic findings;
- preserving the evidence needed for analyst review.

The generated report does not necessarily include every row in the master candidate table.

A message such as:

.. code-block:: text

   Master candidates:   733
   Selected findings:   3

means that 733 candidate rows were reviewed by the generator, but only three were selected for the draft report.

Automatic selection is a prioritisation process. It does not prove that the selected findings are causal or clinically reportable.

20.8 Multiple Findings
----------------------

The JSON structure supports more than one finding in the same report.

A case may contain:

- one main rare-disease finding;
- two variants forming a possible recessive genotype;
- multiple genes associated with the same phenotype;
- a disease-associated variant and one or more pharmacogenomic variants;
- a small variant together with a structural or repeat finding.

Each finding is represented as a separate object in the JSON.

Finding-level information may include:

- finding identifier
- finding type
- finding role
- gene
- chromosome
- position
- reference allele
- alternate allele
- transcript
- coding HGVS
- protein HGVS
- genotype
- zygosity
- consequence
- disease
- inheritance
- classification
- phenotype relevance
- evidence
- confirmation status
- interpretation
- warnings

The browser report must be checked to ensure that rare-disease and pharmacogenomic findings are displayed in the appropriate report sections. Automatic data loading does not remove the need to review the displayed grouping.

20.9 Compound-Heterozygous Findings
-----------------------------------

The generator can preserve compound-heterozygous information produced by the inheritance workflow.

The underlying pipeline distinguishes between:

- phased variants confirmed on opposite haplotypes;
- unphased variants that may be in trans;
- variants with insufficient phase information;
- homozygous variants that should not be counted as compound heterozygous.

Only variants with appropriate shared phase information and opposite haplotypes should be described as phased in trans.

When phasing is unavailable, the report should use cautious wording such as:

Two heterozygous variants were identified in the same recessive

disease gene; phase was not established.

It should not automatically state that the variants form a confirmed compound-heterozygous genotype.

20.10 Repeat-Expansion Findings
-------------------------------

When a repeat-expansion table is available, the generator may include detected repeat findings in the report JSON.

A detected repeat should not automatically be interpreted as pathogenic. The report must consider:

- the repeat locus;
- the estimated repeat size;
- the reference range;
- the disease-specific threshold;
- the reliability of the detection method;
- whether a dedicated repeat-expansion assay is required.

When the pipeline records a repeat as detected but not clinically interpreted, the report should preserve that limitation.

20.11 Pharmacogenomic Findings
------------------------------

The generator can include pharmacogenomic matches from local or official PGx resources.

PGx entries may contain:

- gene;
- variant;
- allele;
- genotype;
- drug;
- phenotype or functional category;
- evidence source;
- guideline information;
- interpretation warning.

These findings are contextual and must not automatically be treated as rare-disease diagnostic variants.

The report must preserve the following caution:

Pharmacogenomic findings should not be used independently to start,

stop or modify a medication or dose.

Many pharmacogenomic interpretations require complete haplotype or star-allele reconstruction. A single matched variant may not provide enough information to assign a reliable metaboliser phenotype.

20.12 Protected Metadata
------------------------

Pipeline result files do not usually contain all report-level patient information. Information such as patient name, date of birth, physician, specimen and dates must be supplied through a protected metadata file.

The reusable template is:

.. code-block:: text

   clinical_report/report_metadata.template.json

For an individual case, the completed metadata file is placed at:

.. code-block:: text

   input/cases/<case_id>/metadata/report_metadata.json

An example structure is:

.. code-block:: text

   {
   "report_title": "GENOMIC VARIANT INTERPRETATION REPORT",
   "analysis_mode": "validation",
   "laboratory": {
   "name": "Genosphere Clinical Genome Center",
   "subtitle": "Educational Genomic Variant Interpretation",
   "signatory": "Prepared for educational demonstration; not clinically signed out."
   },
   "patient": {
   "patient_name": "Synthetic Example",
   "sex": "Other/Unspecified",
   "date_of_birth": null,
   "indication": "Synthetic demonstration case",
   "ordering_physician": null,
   "account_number": null,
   "specimen": "Synthetic GRCh38 VCF dataset",
   "reported_date": null,
   "collected_date": null,
   "received_date": null
   },
   "phenotype_summary": null,
   "gene_information": null,
   "references": [],
   "recommendations": [
   "Clinical correlation is recommended.",
   "Genetic counselling is recommended.",
   "Orthogonal confirmation is recommended before clinical use."

]

.. code-block:: text

   }

The metadata file should contain only information that is appropriate for the intended report.

For real cases, access permissions should be restricted:

.. code-block:: text

   chmod 600 \
   input/cases/<case_id>/metadata/report_metadata.json

This gives read and write permission to the owner while removing access for other users.

20.13 Metadata Precedence
-------------------------

When metadata are supplied, they are incorporated into the report JSON.

Protected metadata may populate:

- report title;
- analysis mode;
- laboratory name;
- laboratory subtitle;
- signatory statement;
- patient name;
- sex;
- date of birth;
- testing indication;
- physician;
- account number;
- specimen;
- report dates;
- phenotype narrative;
- gene information;
- references;
- recommendations.

The generator should not create a realistic patient name, date of birth or physician when these values are unavailable.

Missing values should remain:

- empty;
- null;
- unspecified;
- accompanied by a warning.

This is safer than inserting invented clinical information.

20.14 JSON Output Location
--------------------------

The draft report is written to:

.. code-block:: text

   results/cases/<case_id>/final/report/<case_id>.report_draft.json

For example:

.. code-block:: text

   results/cases/patient_06_pku/final/report/

└── patient_06_pku.report_draft.json

The report directory is created automatically when needed.

The draft suffix indicates that the file has not yet undergone final analyst approval.

A manually reviewed version may later be saved as:

.. code-block:: text

   <case_id>.report_reviewed.json

The reviewed file should not overwrite the original draft unless a controlled versioning policy has been adopted.

20.15 JSON Schema
-----------------

The file:

.. code-block:: text

   clinical_report/report_schema_v1.json

defines the expected structure of the report JSON.

A schema helps ensure that:

- required top-level sections are present;
- values use appropriate data types;
- lists are represented consistently;
- finding objects follow a predictable structure;
- future report builders can interpret the data;
- format changes can be versioned.

The schema version should be preserved in the report JSON so that future versions of the report builder can determine how the file should be interpreted.

A report passing basic JSON syntax validation is not necessarily clinically valid. Syntax validation only confirms that the file is structurally readable.

20.16 Basic JSON Validation
---------------------------

A generated report can be checked with:

.. code-block:: text

   python3 -m json.tool \
   results/cases/<case_id>/final/report/<case_id>.report_draft.json \
   >/dev/null

When no error is displayed, the JSON syntax is valid.

The command does not confirm that:

- all values are correct;
- the selected findings are appropriate;
- the classification is justified;
- patient metadata are accurate;
- the interpretation is clinically complete.

These aspects still require analyst review.

20.17 Checksum Generation
-------------------------

A SHA-256 checksum is created beside the draft JSON:

.. code-block:: text

   <case_id>.report_draft.json.sha256

For example:

patient_06_pku.report_draft.json

patient_06_pku.report_draft.json.sha256

The checksum provides a reproducible fingerprint of the JSON file.

It can detect whether the report JSON has changed since the checksum was created.

The checksum can be verified with:

.. code-block:: text

   cd \
   results/cases/<case_id>/final/report

.. code-block:: text

   sha256sum --check \
   <case_id>.report_draft.json.sha256

A successful result appears as:

<case_id>.report_draft.json: OK

A failed checksum means that the file has changed, become damaged or no longer matches the recorded digest.

A checksum confirms file integrity. It does not confirm interpretation accuracy or report approval.

20.18 Pipeline-Summary Registration
-----------------------------------

The automatic workflow records the report output in:

.. code-block:: text

   results/cases/<case_id>/final/<case_id>.pipeline_summary.tsv

The relevant entries are:

.. code-block:: text

   report_json    results/cases/<case_id>/final/report/<case_id>.report_draft.json
   report_json_sha256    <sha256_digest>

These entries make it possible to locate the report from the final pipeline summary and verify its integrity.

The summary records the generated report path but does not make the report public.

20.19 Generator Warnings
------------------------

The report JSON may contain warnings such as:

- This is an automatically generated draft.
- Analyst review is required.
- This output is not a clinical diagnosis.
- Patient name was unavailable.
- Patient sex was unavailable.
- Pharmacogenomic findings are contextual.
- Orthogonal confirmation was not performed.
- Warnings should remain visible during review.

They should not be removed merely to make the report appear more complete.

A warning identifies an unresolved limitation or a field requiring attention.

20.20 Provenance
----------------

The JSON records provenance so that the report can be traced back to its source workflow.

Provenance may include:

- case identifier;
- generation date;
- pipeline mode;
- generator name;
- schema version;
- source candidate table;
- phenotype source;
- resource-mode information;
- pipeline-summary path;
- number of candidates examined;
- number of findings selected;
- warnings.

This information supports reproducibility and auditing.

The report should always be traceable to the version of the pipeline and resources used to create it.

20.22 Automatic Report Launcher
-------------------------------

The local launcher is:

.. code-block:: text

   clinical_report/open_case_report.sh

It performs the following tasks:

#. Validates the case identifier.
#. Locates the report HTML.
#. Locates the case JSON.
#. Checks that the JSON is valid.
#. Verifies the checksum when available.
#. Confirms that the requested port is free.
#. Starts a local Python HTTP server.
#. Binds the server to 127.0.0.1.
#. Builds a URL containing the report JSON path.
#. Opens the report in the Windows browser.

The command is:

.. code-block:: text

   cd ~/rare_disease_project

.. code-block:: text

   bash \
   clinical_report/open_case_report.sh \
   <case_id>

For example:

.. code-block:: text

   bash \
   clinical_report/open_case_report.sh \
   patient_06_pku

The default port is:

.. code-block:: text

   8765

A different port can be selected with:

.. code-block:: text

   bash \
   clinical_report/open_case_report.sh \
   patient_06_pku \
   --port 8766

20.23 Automatic Data URL
------------------------

The launcher opens a local address similar to:

.. code-block:: text

   http://127.0.0.1:8765/clinical_report/index.html?data=/results/cases/<case_id>/final/report/<case_id>.report_draft.json

The data parameter tells the report builder which JSON file to load.

Without this parameter, the user may need to choose the JSON manually.

With the parameter, the report builder requests the case JSON from the same local server and populates the form automatically.

The browser should display a message indicating that findings were loaded.

20.24 Why a Local Server Is Required
------------------------------------

Opening index.html directly through the filesystem may produce a URL beginning with:

.. code-block:: text

   file://

Modern browsers restrict some file-to-file requests for security reasons. As a result, the HTML may not be permitted to fetch the JSON automatically.

The launcher instead starts:

.. code-block:: text

   python3 -m http.server

This gives the report a local HTTP address:

.. code-block:: text

   http://127.0.0.1:8765

The report builder and JSON are then loaded through the same local server.

20.25 Localhost Privacy
-----------------------

The server is bound to:

.. code-block:: text

   127.0.0.1

This is the loopback address for the local computer.

It means that the report server is intended to be accessed only from the same machine.

The launcher does not deliberately bind to:

.. code-block:: text

   0.0.0.0

because that could make the server available through external network interfaces.

Localhost binding reduces accidental network exposure, but it does not replace proper protection of the computer, user account and case files.

20.26 Stopping the Local Server
-------------------------------

The launcher prints the process identifier of the local server.

A message may appear similar to:

.. code-block:: text

   Server PID: 422

The server can be stopped with:

.. code-block:: text

   kill 422

The launcher also stores a temporary PID file under:

.. code-block:: text

   /tmp/genosphere_report_server_<user>_<port>.pid

Starting the launcher again on the same managed port may stop the earlier server before creating a new one.

The server should be stopped when the report is no longer being reviewed.

20.27 Automatic Population of the Report Builder
------------------------------------------------

When the JSON is loaded successfully, the report builder populates fields from the structured data.

Automatically populated information may include:

- report title;
- laboratory details;
- patient information;
- case identifier;
- testing indication;
- specimen;
- dates;
- phenotype summary;
- methodology;
- gene and disease findings;
- variant coordinates;
- HGVS descriptions;
- genotype and zygosity;
- inheritance;
- classification;
- interpretation;
- confirmation status;
- recommendations;
- limitations;
- references;
- warnings.

The fields remain editable so that the analyst can correct, remove or expand the automatically generated content.

20.28 Nested JSON Values
------------------------

Some evidence fields may contain nested objects or lists rather than plain text.

The report builder must convert these structures into readable text rather than displaying:

[object Object]

The current JSON-enabled report template includes logic for handling nested values more safely.

Nevertheless, the analyst should inspect the complete report for:

- unreadable objects;
- missing values;
- duplicated text;
- incorrect grouping;
- table overflow;
- unhelpful raw field names.

A technically valid JSON file may still require display-level corrections.

20.29 Findings Display and Role Review
--------------------------------------

The JSON may contain different finding roles, including:

primary disease finding

supporting disease finding

compound-heterozygous partner

pharmacogenomic finding

repeat finding

structural finding

The report builder should use finding type and role information when deciding where a result is displayed.

The analyst must verify that:

- diagnostic findings are shown in the main disease section;
- pharmacogenomic findings are not described as diagnostic VUS results;
- repeat findings are labelled as repeat findings;
- supporting variants are not presented as independently diagnostic;
- phase uncertainty remains visible;
- confirmation language is appropriate.

This review is particularly important when one case contains findings from several analysis modules.

20.30 Confirmation Defaults
---------------------------

The automatic workflow uses a conservative confirmation default.

A generated report should state:

Not independently confirmed

or:

Orthogonal confirmation was not performed within this workflow.

The report must not state:

This result was confirmed by Sanger sequencing.

unless independent evidence shows that Sanger confirmation was actually completed.

Confirmation status should be changed only after the supporting laboratory record has been reviewed.

20.31 Saving a Reviewed JSON
----------------------------

After all fields have been checked, the report builder can export a reviewed JSON file.

The suggested filename is:

.. code-block:: text

   <case_id>.report_reviewed.json

The reviewed JSON represents the analyst-edited version of the report.

It should preserve:

- the final selected findings;
- corrected metadata;
- reviewed narrative;
- references;
- recommendations;
- limitations;
- confirmation status;
- warnings that remain relevant.

The reviewed JSON should be stored securely because it may contain patient-identifiable information.

20.32 Exporting the PDF
-----------------------

The final visible report can be exported using the browser’s print function.

The recommended filename is:

.. code-block:: text

   <case_id>.genomic_report.pdf

Before exporting, confirm that:

- all report sections fit on the page;
- long tables do not extend outside the printable area;
- variant text is readable;
- page breaks are reasonable;
- blank sections have been removed or completed;
- warnings and limitations are visible;
- the report is clearly marked as educational or non-clinical when applicable.

The PDF should not be uploaded to a public repository.

20.36 Troubleshooting
---------------------

**Report**** JSON is missing**

Confirm that the case pipeline completed and that the generator exists:

.. code-block:: text

   ls -lh \
   pipeline/case_workflow/22_build_clinical_report_json.py

Regenerate manually:

.. code-block:: text

   python3 \
   pipeline/case_workflow/22_build_clinical_report_json.py \
   <case_id>

**JSON syntax validation fails**

Run:

.. code-block:: text

   python3 -m json.tool \
   results/cases/<case_id>/final/report/<case_id>.report_draft.json

The command will display the approximate location of the syntax error.

Do not manually repair a generated JSON without also determining why the generator produced invalid output.

**Checksum fails**

Regenerate the report or recreate the checksum after confirming that the JSON change was intentional.

A checksum failure must not be ignored.

**Browser opens a folder instead of the report**

The launcher should call Windows PowerShell to open the HTTP URL rather than passing the URL directly to File Explorer.

The browser-launch command should use:

.. code-block:: text

   powershell.exe -NoProfile -Command \
   "Start-Process '$REPORT_URL'"

**Port is already in use**

Use another port:

.. code-block:: text

   bash \
   clinical_report/open_case_report.sh \
   <case_id> \
   --port 8766

**JSON loads but some fields are blank**

Check:
